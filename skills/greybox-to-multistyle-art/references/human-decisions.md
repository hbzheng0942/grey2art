# Reuse decisions; keep review small and observable

## Existing H1–H5 decisions

| Decision | Actual reviewable object | Reuse boundary |
|---|---|---|
| H1 | Candidate images, selected hashes, user comments and priority style | Same selected images/scope |
| H2 | Selected-style atlas and spatial design, major landmarks/transitions/interfaces | Local work inside accepted envelopes/intent |
| H3 | Exact complete-sample references/BOM/assembly, routes and supplier portfolio, explicit models/parameters, sourced costs, wallet/currency caps and repair/fallback scope | Same authorized operations/references/parameters within ceilings |
| H4 | Complete native sample, gameplay/technical checks, visual comparison and open defects | Same proven rules and covered spatial/processing types |
| H5 | Every promised style/scope and exact delivered version | That actual deliverable, not later changed bytes |

Record the actual user source against artifact/stage identity. Silence, task status, agent review, local flags and account balance are not human decisions or spending authority. Reuse existing explicit authorization when it covers these same artifacts/scope; do not ask again for ceremony. H2/H3 may share one presentation with separate bindings. The initial overview, internal first-result checks, polls and ordinary in-scope repairs add no human gate.

H3 uses sourced estimates; API quotes are conditional on actual need. Separate estimates/charges, wallets/currencies and repair reserve; show meaningful alternatives or the sole feasible route. Follow [workflow](workflow-vnext.md) for costing. Exact complete-sample references are required: future delegated-reference acceptance is not implemented, so a budget/early crop alone cannot authorize partial submission.

Keep all selected styles; schedule priority in operational control. Lead H4 releases later styles without waiting for polish; each retains applicable decisions/checks. Changed images/major design revisit affected H1/H2; new supplier/model/paid scope revisits H3 unless already authorized as a bounded substitute. In-scope fitting/material repairs proceed and revalidate. Readiness refresh does not revoke creative approval; unknown submissions recover before retry/switch.

## Three small review moments inside the existing workflow

1. **Before multiplying a method:** inspect the first useful concept, key view or reference-family result already authorized for production. For concepts check space/design/style; for references check identity/completeness/light. Each later image still gets a brief actual-pixel check. Use its current receipt/review notes, not another ledger or user checkpoint.
2. **Before modeling:** inspect the actual complete-sample reference files and BOM/assembly mapping during existing H3 preparation. Confirm intended objects, recognition features, view agreement and real submitted bytes. A parameter/hash check cannot judge appearance.
3. **When a whole native composition first exists:** at S6/H4 compare the approved target and actual gameplay views/states. Name the few biggest omissions or mismatches, route them to design/asset/assembly/rendering, and fix the largest useful one first. S6 may show unfinished final-art layers as planned work; unresolved spatial/observation risks still block H3.

For each review use `pass`, `fail` or `unclear` plus a concrete observed region/state. Record at most the useful facts: **observation → main defect → next action → expected visible change**. These are notes within existing schemas; do not replace required receipts or invent schema fields. Open the actual pixels before claiming a visual pass. Missing visibility/capability means `unclear`, with scope named; a required failed/unclear check remains unresolved. Unseen optional scope is unreviewed, not implicitly passed. A self-review is a screening observation, not independent or human acceptance. A changed input+prompt/asset+light pair establishes only that combined result, not a causal claim about either variable.

Before H1–H5 retain machine checks and one current bound review. Use [workflow review protocol](workflow-vnext.md#lightweight-pre-handoff-review) for inputs/receipts. Prefer independence; otherwise declare `unverified_serial` and its limitation. Bind review before human approval; reuse still-current production observations without another full audit. Approval flags cannot repair missing/stale evidence or material failures.

## Repair only what the observation supports

Freeze target, camera/state and budget. Normally allow 2–3 focused repairs, within actual authority; this grants no paid calls. In existing [production control](production-control.md), start each attempt before work and record stable defect/asset ID, method, actual effort and before/after evidence. New scripts/workers/runs do not reset counts; cloud wait is not active repair.

Two attempts without meaningful visible improvement require a method change or concrete tradeoff, not another wording variation. A material failure cannot become polish because time ran out. At the cap, use a verified authorized fallback, defer a genuinely nonblocking item, or present the specific unresolved decision; continue unaffected work. Reassess the largest visual gap after roughly 20–30 active minutes/two local corrections. Reviewing an unchanged image is not progress.

Present actual images/diff, observations, unresolved defects and changed scope/cost; ask only the needed existing decision. Keep technical/gameplay/art/performance/human status distinct. Preserve historical decisions/recovery IDs and canonical assets; changed bytes invalidate affected evidence/approvals under the workflow contract.

## Playable H5 recording

Run `greybox.py delivery-review-inputs --run-dir RUN`; review final native evidence against concepts/H3 and accepted samples. Save the real `{producer, receipt}` using `record-delivery-review --run-dir RUN --file REVIEW.json`, then run `delivery-manifest --run-dir RUN` and present the exact delivery/hash. After the real user response, use `accept-delivery --run-dir RUN --actor user --source-ref ACTUAL_MESSAGE --note ACTUAL_DECISION --manifest-hash HASH`.

This bundled H5 CLI requires a complete Godot/Unity production run with playable validation, all promised styles/baseline spaces and current native technical/gameplay checks. A fixture/proxy or lead-style partial run is ineligible. Consolidate canonical existing resources without regeneration/full-tree copies. Changed native inputs/outputs/reports/captures invalidate affected acceptance; capability expiry alone does not. The host records the user's decision, never originates it.

## Native spatial delivery

For an explicitly spatial Blender authoring or art endpoint, use the [native authoring route](greybox-authoring.md): present the exact editable `.blend`, source/dependency identity, affected native views, agreed spatial/art checks and remaining defects. Record the actual user's acceptance against that spatial deliverable in the owning task. Applicable design and paid-production decisions still bind their own scope. Do not run the playable H5 CLI, fabricate gameplay checks or require a future game runtime merely to accept a spatial deliverable. Later game integration needs its own native gameplay evidence; spatial acceptance does not supply it.
